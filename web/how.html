仕組み

Surfactant は BungeeCord式のプロキシです。プレイヤーは Surfactant にだけ接続し、Surfactant が行き先のバックエンドのプロトコルに揃えてから渡します。後ろのサーバーは自分のプロトコルで来た接続だけを受ければよく、内部変換がいりません。

流れ

クライアント

Java クライアント（1.19〜26.2）と Bedrock クライアントが、Surfactant に接続します。

Java TCP 25565
Bedrock UDP 19132

Surfactant

経路表で行き先を決め、クライアントのプロトコルをバックエンドのプロトコルに揃えます。/server での移動と、転送信頼の署名もここで行います。

経路表・振り分け
プロトコル正規化の判定
/server コマンド
転送信頼の署名

バックエンド

ロビー・サバイバルなどのサーバーです。DetergentMC やバニラサーバーを置きます。バックエンドごとにプロトコルが違ってかまいません。

lobby — 127.0.0.1:25566（776）
survival — 127.0.0.1:25567（763）

設定は surfactant.yml に書きます。バックエンドは backends に複数登録し、default-backend で既定の行き先を指定します。

プロトコル正規化

判断は「同じ→素通し、古い→上向き、新しい→下向き」の1か所に集まっています。翻訳そのものは DetergentMC のエンジンが行います。正規化は移動のたびに行うので、移動先が変われば判断も変わります。

クライアントバックエンド判断
776776素通し（バイト列をそのまま中継）
763776上向きに翻訳（エンジン）
776763下向きに翻訳（エンジン）
未対応のプロトコル776断る（未対応の切断メッセージ）

/server での移動

プレイヤーは Surfactant に接続すると、まず既定のバックエンド（例：lobby）に入ります。/server で移動できるバックエンドの一覧を見られ、/server <名前> で別のバックエンドへ移動します。

  • Transfer パケット（766・1.20.5 以降）：サーバー側が Transfer パケットを送り、クライアントが自分で指定のアドレスへ接続し直します。切断なしで移動できます。
  • 再接続フロー（765 以前）：Transfer パケットがないため、プロキシ側で「切断→再ログイン相当の流れ」を作ります（BungeeCord式）。
  • 土台の段階では：経路表・既定バックエンドへの参加・/server コマンドの解釈と移動要求の組み立て・方式の判定までが動きます。実際の移動の実行（Transfer パケットの送信、再接続フローの実装）は次の段階です。/server は今のところ要求を作るだけで、移動しません。

Bedrock の変換

Bedrock Edition のクライアントも、同じ Surfactant で受け付けます。UDP 19132 番で待ち受け、RakNet プロトコル 30 個に対応しています。変換は DetergentMC のエンジン（Geyser風）が行います。

  • チャンク・エンティティの翻訳：Java のブロック状態を Bedrock のランタイム ID に変換します。バイオームやエンティティも変換します。加入・チャット・移動までが土台の目標です。
  • Floodgate風の認証：Java アカウントがなくても入れます。Xbox の XUID から決定的な UUID を作り、名前の先頭に . を付けます（既定の接頭辞は .）。
  • 制限：インベントリはエンジン側で未対応です。Xbox 署名の検証や暗号化はまだなく、NACK による再送もありません。最新の Bedrock 26.60 / 26.62 には未対応です。

転送信頼

Surfactant と後ろのサーバーのあいだでだけ共有する秘密で、転送するプレイヤー情報に署名します。後ろのサーバーは署名を検証し、合うものだけを「Surfactant 経由の信頼できる接続」として受け入れます。

  • 方式：共有シークレットで HMAC-SHA256 署名します（考え方は Velocity と同じですが、形式は Surfactant 独自のもので、Velocity とバイト互換ではありません）。
  • 設定：forwarding.mode（none／velocity）と forwarding.secret を指定します。velocity のとき secret が空だと起動時にエラーで止まります。
  • 土台の段階では：Surfactant 側の署名・検証とペイロードの組み立てまでが動きます。DetergentMC 側の受け入れ（署名の検証と、検証済み接続の信頼）は次の段階です。

online-mode認証とリソースパック

  • online-mode認証：翻訳が必要な接続では、Surfactant が Mojang 認証（hasJoined）を自分で完結させ、認証済みの接続だけを内部のバックエンド（offline-mode・信頼済み接続）へ繋ぎます。素通しの接続では暗号化ハンドシェイクもそのまま通します。
  • リソースパック：クライアントのプロトコルに合うパックをエンジンが選びます。外部 HTTPS 配信を使う場合は resource-pack.url（https:// のみ）と resource-pack.sha1 を指定します。空ならループバック配信です。公開用の HTTPS 置き場はまだ決まっていません。

正直な話

  • 本物のゲームクライアントでの確認は、まだどの組み合わせも行っていません。検証はプロトコルレベル（偽クライアントと本物のバニラサーバー）です。
  • 実際のサーバー移動はまだ動きません。土台の段階では /server は移動要求を作るところまでです。プレイヤーリストの統合も設計だけで、実装は次の段階です。
  • エンジンの制限も引き継ぎます。Java 側のチャンク翻訳は、ブロック値の誤訳の疑いがあることが分かっています（調査中です）。Declare Recipes／Statistics／Tags／World Event ID はエンジン側で全方向で未対応です。
